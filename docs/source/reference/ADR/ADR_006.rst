ADR 006 — ibis-native DSL experiments and performance tradeoffs
===============================================================

.. warning::
    **Historical Document**: This ADR describes historical experiments and a proposed DSL (v21) that differs from the final v1 implementation.
    The current ``Ledger`` implementation does not support ``transaction()`` or ``session()`` directly on the ledger object; instead, use the ``earlysign.v1.framework.Session`` context manager.
    Refer to ``docs/source/explanation/concepts.md`` for the authoritative design documentation.

Summary
-------

**Goal:** deliver a ledger-first DSL that is ibis-native enough to export SQL, fast enough to run in notebooks (<1–2 s/update), and faithful to the event-sourcing model (every state is written/read via the ledger).

**How:** combine (a) a reusable ``Ledger`` core with ``transaction()``/``session()`` helpers, (b) stage helpers that materialise snapshot/info/stat rows, and (c) either cached ibis plans or Python arithmetic, depending on the use case. Explicit DuckDB (or BigQuery) transactions keep updates in a single scope, and literal inserts avoid recursion.

**Status:** With the current v21-style DSL (stage materialisation + Python arithmetic + transactions), we meet the performance (<~1.1 s), maintainability, and event-sourcing requirements. If we need ibis-native math for auditing, we can reintroduce cached plan templates (option 2 below) without changing the user-facing DSL.

Current DSL recommendation
--------------------------

Based on the profiling work below, the most practical DSL today is a two-tier pattern
built directly on the ``Ledger`` ecosystem:

.. code-block:: python

    ledger = Ledger(con, "ledger_name", labels={"experiment_id": "exp"})  # setup elsewhere

    with ledger.transaction():              # single DuckDB transaction per update
        snapshot_prev = snapshot_stage.latest_payload()
        snapshot_next = {...}               # Python arithmetic, ledger-centric
        with ledger.session() as sess:      # emits literal rows (observation, snapshot, info…)
            snapshot_stage.emit_from_dict(sess, snapshot_next)
            info_stage.emit_from_dict(sess, {"info_time": ...})
            stat_stage.emit_from_dict(sess, {...})
            # downstream operators (e.g., BinomialABTestV21) compose these pieces

Why both ``transaction()`` and ``session()``?

* ``transaction()`` issues ``BEGIN/COMMIT`` on the DuckDB connection so all reads/inserts share a single transaction; it is about **DB-level scope** and keeping the REPL fast (no implicit auto-commit per statement).
* ``session()`` remains the insertion DSL: it normalises payloads (UUID/timestamp/version), enforces label scoping, and gives us a future hook to reintroduce queued inserts if we ever need lazy/batched writes again.

The names reflect their roles (DB transaction vs. logical write session). We could merge them later, but keeping them separate makes it clear that users can open a read-only transaction without emitting rows, or emit rows outside an explicit transaction when they really need to. The recommended pattern is to nest them exactly once per update as shown above.

Minimal backend-agnostic DSL
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

To make this concrete, the DSL only needs a tiny abstraction layer so different backends (DuckDB, BigQuery, …) can share the same ``transaction/session/stage`` API:

.. code-block:: python

    class LedgerBackend(Protocol):
        @contextmanager
        def transaction(self):
            ...

        def insert_rows(self, table: str, rows: list[dict[str, Any]]) -> None:
            ...


    @dataclass
    class DuckDBBackend(LedgerBackend):
        con: ibis.backends.BaseBackend

        @contextmanager
        def transaction(self):
            try:
                self.con.raw_sql("BEGIN")
                yield
                self.con.raw_sql("COMMIT")
            except Exception:
                self.con.raw_sql("ROLLBACK")
                raise

        def insert_rows(self, table: str, rows: list[dict[str, Any]]) -> None:
            self.con.insert(table, rows)


    @dataclass
    class BigQueryBackend(LedgerBackend):
        client: "google.cloud.bigquery.Client"

        @contextmanager
        def transaction(self):
            tx = self.client.transaction()
            tx.begin()
            try:
                yield
            except Exception:
                tx.rollback()
                raise
            else:
                tx.commit()

        def insert_rows(self, table: str, rows: list[dict[str, Any]]) -> None:
            self.client.insert_rows_json(table, rows)


    class LedgerSession:
        def __init__(self, backend: LedgerBackend, table_name: str, labels: dict[str, Any]):
            self.backend = backend
            self.table_name = table_name
            self.labels = labels

        def insert(self, kind: str, payload: dict[str, Any]) -> None:
            now = datetime.utcnow()
            row = dict(
                id=str(uuid.uuid4()),
                ts=now,
                pkg_version=__version__,
                kind=kind,
                labels=json.dumps(self.labels),
                payload=json.dumps(payload),
            )
            self.backend.insert_rows(self.table_name, [row])


    @contextmanager
    def ledger_session(ledger) -> Iterator[LedgerSession]:
        session = LedgerSession(ledger.backend, ledger.table_name, ledger.labels)
        yield session

With this shim in place, the DSL stays identical across DuckDB and BigQuery—the only difference is the backend injected during ``Ledger`` construction.  All of the scripts discussed below ultimately desugar into this pattern.

Desired properties and trade-offs
---------------------------------

.. list-table::
   :header-rows: 1

   * - Property
     - Why we want it
     - How to achieve it
     - Risks / lessons from experiments
   * - **Fully ibis-native computations**
     - Enables SQL export/auditing, keeps formulas close to academic notation.
     - Encode Φ, Φ⁻¹, spending functions via ibis primitives (v10/v11), reuse plan templates (v16 idea).
     - ``con.insert`` recursion (v9, v19), huge AST compilation (v11), high runtime (47 s) unless we cache or simplify queries because of SQL compilation.
   * - **Event-sourcing discipline**
     - Deterministic replays, ability to inspect every intermediate state.
     - Stage helpers that insert snapshot/info/stat rows + re-read them before use (v18–v21).
     - Must ensure reads go through ledger (early v20 skipped info_prev re-read). More stages mean more inserts unless batched.
   * - **Low runtime (<1–2 s/update)**
     - Keeps notebooks responsive, enables rapid experimentation.
     - Shift heavy math to Python (v20 refactor), use literal inserts, wrap updates in transactions (v21).
     - SQLGlot compilation still shows up for every ``execute``/memtable; need caching or staged literals to go lower.
   * - **Backend portability (DuckDB + BigQuery)**
     - Same DSL should work locally and in cloud warehouses.
     - Thin backend adapters (see code above) with `transaction()` + `insert_rows`.
     - BigQuery transactions and insert APIs differ (JSON payload, quotas); need retry/error handling, but DSL stays unchanged.
   * - **Readable, declarative DSL**
     - Users think in terms of ledger events, not plumbing.
     - Stage DSL (``snapshot_stage.emit(...)``) + `with ledger.transaction():` scaffolding.
     - Too much “magic” (deep cached plans) can hurt debuggability; document the layers clearly.

Key experiments and what we learned
-----------------------------------

v1: struct payload baseline
~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** prove that a single STRUCT payload ledger plus ibis expressions can cover the entire Lan–DeMets procedure within one SQL insert per update.
- **Implementation:** ``BinomialABTest`` unions observation/snapshot/info/stat/decision expressions and executes a single ``INSERT … SELECT`` inside a manual ``BEGIN/COMMIT``.
- **Performance:** 0.29 s for two updates; ``_build_insert_from_table`` (0.17 s) and ``con.insert`` (0.23 s) dominate the profile.
- **Lesson:** Pure ibis already works, but every update recompiles a large SELECT and the STRUCT schema is inflexible—pushing us toward JSON payloads in v2.

v2: staged LedgerSession with JSON payloads
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** offer an ergonomic read-after-write DSL via ``LedgerSession`` while keeping everything ibis-native.
- **Implementation:** sessions buffer ibis expressions (observation, snapshot, etc.) and flush them via a batched ``INSERT … SELECT`` into a JSON payload column.
- **Performance:** 0.46 s for two updates; ``LedgerSession.__exit__ → flush → con.insert`` costs 0.35 s because DuckDB must still parse the staged SELECT.
- **Lesson:** The DSL improves usability, yet the INSERT compilation overhead remains unchanged.

v3: shared ledger for AB test + E-process
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** reuse one ledger/session stack for both the binomial GST and the normal-mixture E-process without Python JSON munging.
- **Implementation:** ``_real_flat_view`` projects JSON into typed fields so apps can add ibis literals on top of committed aggregates.
- **Performance:** 0.58 s (two updates) with ``flush → con.insert`` still taking ~0.41 s.
- **Lesson:** Multiple apps can coexist, but adding more views only increases the cost of the inevitable insert-from-select.

v4: labels-bound ledger contract
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** lock in the ``(uuid, ts, pkg_version, payload_type, payload, labels)`` schema and introduce ``Ledger.bind`` for scoped reads.
- **Implementation:** inserts auto-fill uuid/ts/pkg_version; readers consume the same JSON view.
- **Performance:** 0.64 s (two updates); parsing the richer schema keeps ``_build_insert_from_table`` and ``con.insert`` as the bottleneck.
- **Lesson:** We now have the table contract we like, but still no path around insert compilation.

v5: projector framework (single design row)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** split responsibilities between a reusable ``Ledger`` framework and application-specific ``FlatProjector`` helpers while storing the entire design in one row.
- **Implementation:** projectors synthesize design helper rows; updates still flush via ibis SELECT. Four updates were run to exercise multiple looks.
- **Performance:** 1.57 s total (~0.39 s/update). ``flush`` and ``_build_insert_from_table`` dominate (>1.0 s combined).
- **Lesson:** The DSL becomes pleasant, but runtime scales almost linearly with the number of staged batches because inserts are still expression-based.

v6: minimal projectors, inline SQL
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** shrink projector SQL (no NULL padding, inline snippets) to curb plan size.
- **Implementation:** ``ABBaseRows``/``EBaseRows`` emit compact SELECTs; ``LedgerSession`` is unchanged.
- **Performance:** 0.997 s for four updates (~0.25 s/update); ``con.insert`` + SQL parsing stay on top.
- **Lesson:** Leaner projectors help a bit, yet INSERT compilation continues to be the ceiling.

v7: reader hierarchy with profiling hook
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** build reusable reader classes (``ABDesignLatest``, ``ABObsSince``, etc.) and add a ``__main__`` profiling harness.
- **Implementation:** generic helpers such as ``rows_since`` feed the readers; writes are untouched.
- **Performance:** 1.06 s for four updates; parser/``_build_insert_from_table`` remains the bottleneck because every reader adds SELECT depth.
- **Lesson:** DSL clarity improved but cost per insert did not.

v8: generic latest()/rows_since() helpers
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** generalize the reader DSL so any payload type can rely on ``latest_row``/``rows_since`` without bespoke SQL.
- **Implementation:** ``LedgerReaderBase`` centralizes the helper logic; apps re-use it for AB + E workflows.
- **Performance:** 1.22 s for four updates; ``dialect.parse`` (0.52 s) and ``_build_insert_from_table`` (0.71 s) dominate before inserts run.
- **Lesson:** The reader abstraction is portable, but until inserts stop compiling huge SELECTs the runtime cannot improve—leading directly to the literal-insert experiments in v9+.

v9: first ibis-native event-sourcing pipeline
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** implement the full Lan–DeMets workflow purely in ibis, sending each event via ``INSERT … SELECT``.
- **Result:** runtime ~1.15 s. Profiling shows ``Ledger.flush → con.insert → raw_sql`` dominating because every insert compiled a plan that read from the same ledger table (risking recursion).
- **Lesson:** pure ibis is feasible, but self-referential inserts already push SQLGlot to its limits; we need lighter insert paths before adding more laziness.

v10: SQL-only boundary approximation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** remove Python math entirely by encoding Φ, Φ⁻¹, and spending functions pure-SQL (Abramowitz–Stegun polynomials).
- **Implementation:** pure ibis SQL for all math; after updating to ``ibis.cases`` the script runs again.
- **Performance:** ~2.0 s; still dominated by ``flush → con.insert → raw_sql`` and large expression depth (action node depth 19).
- **Lesson:** pure SQL approximations are possible but still suffer from INSERT plan compilation; faster than v19 but slower than Python hybrids.

v11: frozen views and DB-evaluated timestamps
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** evaluate timestamps on the database side and read all state via “frozen” views (ts < latest observation).
- **Result:** 39 s runtime. Bottleneck: `_insert_select_sql` issues huge `raw_sql` statements per stage; query depth explodes even though recursion is avoided.
- **Lesson:** even when ibis math is elegant, repeatedly compiling insert-from-select queries dwarfs everything else.

v12: staged INSERT/SELECT helper
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** refactor v11’s INSERT/SELECT into reusable helpers, hoping to amortize compilation.
- **Result:** runtime dropped to 14 s, but `_insert_select_sql` still dominates (DuckDB must parse the SELECT every time).
- **Lesson:** abstraction alone doesn’t remove the compile cost—we need a different insertion strategy.

v13: literal inserts + aggregator objects
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** switch the pipeline to literal dict inserts (via ibis memtable) while keeping ibis math for stats/boundaries; introduce aggregator objects for readability.
- **Result:** runtime ~0.83 s. Bottleneck shifts to memtable compilation, which is manageable.
- **Lesson:** once inserts become literal, we regain the sub-second performance envelope.

v14/v15: hybrid vs. pure Python
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** keep ibis-native state but avoid expensive queries per stage.
- **Result:** pulling `_state_with_due_frame` into pandas (v15) gives ~0.6 s runtime
 while staying event-sourced (writes were still ledger inserts). ibis math remains in code but
 simultaneous ledger reads/writes are limited.
- **Lesson:** Python arithmetic is extremely fast; ledger writes themselves are cheap
 when they are literal dicts (memtable select).

v16: cached plan template (expr.op().replace)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** cache the ibis operator tree produced by ``_state_with_due_frame`` and reuse it by replacing the delta placeholder each update.
- **Implementation:** ``template = expr.op()`` at setup, ``template.replace({delta_placeholder: delta_expr.op()}).to_expr()`` at runtime.
- **Performance:** ~1.2 s (profiling shows ``_execute_state_plan`` → ``con.execute`` as the main cost).
- **Trade-offs:** still ibis-native, but each replace leads to a new SELECT that DuckDB must compile; faster than v19 but slower than pure Python.

v17: staged memtables with cached lookups
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** reuse stage information stored in the ledger via helper memtables / aggregator objects while still expressing decisions in ibis.
- **Implementation:** aggregator reads latest snapshot/info/stat into Python, builds small memtables only for incremental deltas, and emits literal inserts.
- **Performance:** ~1.0 s; bottleneck shifts to memtable construction and template lookup.
- **Trade-offs:** good readability, near-baseline speed, but still not purely ibis-native (math happens partly in Python aggregators).

v18: define-by-run session DSL
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** express updates as ibis-native DSL operations within ``with session``.
- **Implementation:** stage rows (snapshot/info/stat) still read via ``latest_json`` (execute),
  arithmetic performed in Python, payloads inserted as dicts.
- **Performance:** ~0.6 s (similar to v15).
- **Trade-offs:** event sourcing remained intact, but math not in ibis.

v19: fully ibis-native lazy pipeline
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** keep entire pipeline (snapshot deltas, I0/I1, boundaries) as ibis expressions.
- **Implementation:** each stage was an ibis expression applied inside ``sess.insert``.
- **Issues:** DuckDB/SQLGlot recursion when ``INSERT … SELECT`` reads from target table;
  after switching to ``raw_sql`` each insert still compiled huge plans → ~47 s runtime.
- **Lesson:** Reusing shared expression trees causes both recursion and heavy SQL compilation.

v20 early: stage DSL + eager execute
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** keep ibis-native stages but materialise intermediate rows. Inserts executed via `execute()` + literal insert to avoid recursion.
- **Outcome:** still slow (45 s) because each stage read/insert triggered full query compilation (duckdb.to_arrow_table → SQLGlot).
- **Fix:** move arithmetic to Python (fetch stage payload dicts, compute in Python, insert literal). Runtime dropped to ~0.9 s.
- **Lesson:** Stage DSL alone doesn’t help unless intermediate math also avoids re-running the heavy ibis plans.

v21: reuse DuckDB connection + transaction scope
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- **Goal:** reuse one DuckDB connection and wrap updates in explicit transactions (``BEGIN``/``COMMIT``) so ibis doesn’t auto-open per statement.
- **Implementation:** added ``Ledger.transaction()`` context, used it around `set_design` and `update` (both AB and e-process).
- **Performance:** ~1.1 s overall → still dominated by repeated ledger reads/inserts but no per-insert transaction overhead.
- **Lesson:** Transactions help but SQL compilation (execute calls, Stage seeding) is still the top cost.

Recurring bottlenecks
---------------------

1. **SQL compilation cost (duckdb.to_arrow_table → SQLGlot).** Each ``execute`` / stage insert compiles a memtable select. This was ~20 s in v19 and still a few hundred ms in v21.
2. **Self-referential inserts.** ``con.insert`` cannot handle queries that read from the target ledger → recursion crash. Workarounds: raw SQL, eager execute to Python, or staging into separate tables.
3. **Plan depth / union defaults.** Unioning default rows + JSON unwrap + cross joins per stage makes the AST large.
4. **Insert count.** Each update writes observation, snapshot, info, stat, decision (and default seeds). More inserts → more memtable compilation.
5. **Transactions.** Without `BEGIN`/`COMMIT`, DuckDB implicitly wraps each statement; explicit transaction reduces overhead slightly but not the core compile cost.

----------------------------

+-----------+--------------------------------------+------------------------------------+----------------------------------------------------+
| Option    | DSL idea                             | Key benefits                       | DSL sketch                                         |

| Stage +   | Cache ibis operator tree once, then  | ibis-native math, reproducible SQL | ``template = stats_expr.op()``                     |
| cached    | ``replace`` delta placeholder each   | without re-compiling huge plans    | ``payload = template.replace({...}).to_expr()``    |

+-----------+--------------------------------------+------------------------------------+----------------------------------------------------+

+-----------+--------------------------------------+------------------------------------+----------------------------------------------------+
| Prepared  | Pre-generate SQL text or prepared    | No SQLGlot compile per insert;     | ``sql = 'INSERT INTO ... VALUES (? , ? , ...)'``   |

|           |                                      | derived outside ibis.              |                                                    |
+-----------+--------------------------------------+------------------------------------+----------------------------------------------------+
| Intermediate staging tables | Store snapshot/info/stat in lightweight DuckDB tables (or ledger kinds) and read via ``ORDER BY ts DESC LIMIT 1``. | Makes every downstream query tiny, keeps DSL close to ibis. | ``latest_snapshot = ibis.table('snap_stage').order_by('ts').limit(1)`` |
+-----------+--------------------------------------+------------------------------------+----------------------------------------------------+
| Tx-scoped caching | Provide a small DSL helper that caches stage payloads inside ``with ledger.transaction():`` so repeated reads hit Python memory unless a write occurs. | Reduces ``execute()`` churn; still event-sourced. | ``with ledger.transaction():\n    cache = StateCache(ledger)\n    snap = cache.snapshot()\n`` |
+-----------+--------------------------------------+------------------------------------+----------------------------------------------------+
| Hybrid    | Keep key formulas (e.g., boundaries) | Best of both worlds: ibis for math | ``boundary_expr = boundary_template.with(...)``    |
|           | as ibis expressions, but evaluate    | tracing, Python for orchestration. | ``boundary = ledger.con.execute(boundary_expr)``   |
|           | once per tx and store literal row.   |                                    | ``decision_stage.emit(sess, {..., 'boundary': b})``|

Example: stage + cached ibis plan::

    stats_tpl = stats_expr.op()
    plan = stats_tpl.replace({delta_placeholder.op(): delta_expr.op()}).to_expr()
    with ledger.session() as sess:
        sess.insert(kind="stat", payload_expr=plan)

Example: stage + Python arithmetic (current v21)::

    snap_prev = snapshot_stage.latest_payload()
    snap_next = {...}
    with ledger.transaction():
        with ledger.session() as sess:
            snapshot_stage.emit_from_dict(sess, snap_next)
            info_stage.emit_from_dict(sess, {"info_time": total_now / Nmax})

These snippets illustrate the DSL flavour of the two extremes: either users manipulate ibis expressions directly (`plan = stats_tpl.replace(...)`) or they work with Python dicts backed by stage helpers. Prepared statements and hybrid approaches would expose similar helpers—e.g., `ledger.prepared.insert('decision', columns=[...])`—so the DSL remains declarative even when the backend strategy changes.

In DSL terms:

- **Stage + cached ibis plan** keeps the “define-by-run” feel: users chain ibis ops (`snapshot >> stats >> decision`) and the runtime swaps only the delta placeholder. The DSL remains highly portable (same expressions can render to SQL in other backends).
- **Stage + Python arithmetic** feels almost like a PyData pipeline: ``snap = stage.snapshot(); stage.decision.emit(sess, compute(snap))``. It's readable, easy to debug, and users still reason in terms of ledger events.
- **Prepared inserts** would surface as ``ledger.prepared('decision').emit(payload_dict)``—explicit yet declarative—and make it obvious when stage boundaries are reused across experiments.
- **Intermediate staging tables** turn every “latest” read into ``stage.latest()`` without caring whether it hits the ledger or a helper table, keeping the DSL consistent.
- **Transaction-scoped caching** lets us expose ``with ab.transaction()`` so notebooks look like: ``with ab.transaction(): snap = ab.snapshot(); stats = ab.stats(snap)``—very approachable while ensuring ledger-centric discipline.
- **Hybrid** DSL keeps ibis-level constructs available for teams that need to see/emit SQL while still using the stage helpers for orchestration.

Checklist for future DSL iterations
-----------------------------------

- **Prefer literal inserts** unless you absolutely need to express the insert as a SELECT.
- **Cache or precompile heavy ibis expressions** (particularly unions, cross joins) or move the math into Python.
- **Materialise every state in the ledger** and **read it back** before use to stay event-sourced.
- **Batch work per transaction** (``with ledger.transaction():``) so DuckDB doesn’t auto-open new transactions for each statement.
- **Monitor bottlenecks** with `cProfile` and look for `duckdb.to_arrow_table`, `generator.py:sql`, `con.insert`. Optimize those before touching math.
